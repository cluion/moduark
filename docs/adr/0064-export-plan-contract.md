# ADR-0064: Export Plan Contract

- Status: Accepted; materialization added by ADR-0065 and dependency mapping by ADR-0068
- Date: 2026-08-29

## Context

An extractability report can authorize planning, but copying a Module directory
still does not define a Composer package. Standalone and nwidart layouts place
code and resources at different roots, package identity cannot be safely guessed
from a Laravel application, and an existing destination can make a valid source
plan destructive.

## Decision

- `moduark:export <module> --dry-run` creates a deterministic, read-only package
  plan. Calls without `--dry-run` are rejected until materialization has its own
  atomic write and standalone-installation gate.
- `--target`, `--package`, and `--namespace` are required. The target must be an
  application-relative portable path; Composer package names must be lowercase
  `vendor/name` identities; namespaces must be explicit PHP namespaces.
- Planning reuses the complete extractability report. Any existing extraction
  blocker produces `MOD-EXPORT-EXTRACTABILITY-001` and no file inventory.
- Both supported source layouts map to package roots: Module code to `src/`,
  tests to `tests/`, config, routes, resources, and migrations to their matching
  package directories. Root `composer.json` and nwidart `module.json` are not
  copied because package metadata is generated by the export contract.
- The plan includes generated `composer.json` and package ServiceProvider
  targets, copy operations, and explicit PHP namespace-rewrite transforms. It
  does not generate their contents in this slice.
- Existing destination files, duplicate destinations, linked target ancestors,
  or linked/unsupported source entries block with stable export codes.
- Runtime requirements for `cluion/moduark` and `illuminate/support` are explicit.
  A Module dependency has no implicit Composer identity; without a reviewed
  package/constraint/namespace mapping defined by ADR-0068 it is reported as
  manual and blocks readiness.

## Blocker codes

- `MOD-EXPORT-EXTRACTABILITY-001`
- `MOD-EXPORT-TARGET-001`
- `MOD-EXPORT-SOURCE-001`
- `MOD-EXPORT-COLLISION-001`
- `MOD-EXPORT-DEPENDENCY-001`

## Boundaries

This contract does not write files, infer third-party Composer or frontend
requirements, rewrite PHP, execute publishing, or prove that the planned package
installs under Testbench. Those guarantees belong to the materialization slice.

## Consequences

Automation can review exact file, namespace, dependency, and collision evidence
before any package directory exists. Requiring explicit identity makes plans
slightly more verbose but prevents application or Module names from silently
becoming public package contracts.
